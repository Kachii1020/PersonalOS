# 결정 로그

## 2026-08-12 — 매크로 지표는 주 1회 수집

- **결정**: fetch-macro 크론을 주 1회(월요일)로 설정. FRED/ECOS 매크로 지표는 월별/분기별 발표라 매일 돌릴 필요 없다.
- **이유**: 무료 API 키의 일일 호출 한도를 아끼고, 실질적으로 값이 바뀌는 빈도에 맞춘다.
- **버린 대안**: 시세 잡과 합쳐서 매일 돌리기 — 거의 같은 값을 반복 upsert하는 낭비.

## 2026-08-12 — Notion 미설정 DB는 빈 배열 (에러 아님)

- **결정**: Research Notes, Course Notes, Algo Patterns 레포는 환경변수 없으면 `[]` 반환. UI는 섹션 자체를 숨긴다.
- **이유**: Wiki는 에러를 던지지만(핵심 기능), 나머지 3개 DB는 보조 정보라 없어도 페이지가 떠야 한다.
- **버린 대안**: Wiki처럼 에러 던지기 — 사용자가 Notion에 5개 DB를 전부 만들어야 앱을 쓸 수 있게 되는 건 과하다.

## 2026-08-06 — 환경변수는 database ID로 받고 data source ID는 앱이 변환한다

- **결정**: `NOTION_DB_*`에 URL에서 얻는 database ID를 그대로 넣게 하고, `describeDatabase()`가 `GET /v1/databases/{id}`로 data source ID를 얻어 조회에 쓴다.
- **이유**: Notion API 2025-09-03부터 조회 엔드포인트가 `/v1/data_sources/{id}/query`로 바뀌어 database ID로는 조회가 안 된다. 그런데 사람이 URL에서 바로 복사할 수 있는 값은 database ID뿐이다. 변환을 앱이 떠맡으면 설정 단계가 하나 줄고, SPEC 4절의 환경변수 이름도 그대로 간다.
- **버린 대안**: data source ID를 직접 넣게 하기 — Notion UI의 `Manage data sources`까지 들어가야 해서 설정 실패 지점이 늘어난다. 클라이언트는 두 값 다 받으므로 원하면 직접 넣어도 된다.

## 2026-08-05 — 강의자료 요약 프롬프트에 앞 24,000자만 넣는다

- **결정**: `MAX_CHARS = 24_000`으로 자르고, 잘렸다는 사실을 프롬프트에 명시한다.
- **이유**: 강의 슬라이드 한 개가 5만 자를 넘는 경우가 있다. 버튼 한 번에 그만큼을 태우면 월 예산이 몇 번의 클릭으로 사라진다. 목차와 본론은 앞부분에 있어 요약 품질 손해가 크지 않다.
- **버린 대안**: 전체를 넣고 예산 가드에 맡기기 — 가드는 사후에 막을 뿐, 이미 쓴 돈을 되돌리지 않는다.

## 2026-08-05 — PPTX는 전용 라이브러리 없이 OOXML zip을 직접 읽는다

- **결정**: `fflate`로 압축을 풀고 `ppt/slides/slideN.xml`의 `<a:t>` 런만 모은다. 키 이름으로 재귀 수집한다.
- **이유**: PPTX 파서 패키지는 대부분 렌더링·편집까지 포함해 무겁다. 필요한 건 본문 텍스트뿐이고, `<a:t>`는 도형·표·자리표시자 어디에 있든 같은 태그다. XML 경로를 가정하지 않으면 레이아웃이 달라도 안 깨진다.
- **버린 대안**: officeparser류 도입 — 의존성 무게 대비 얻는 게 텍스트 하나뿐이다.

## 2026-08-05 — 과목 코드는 정규식을 조이는 대신 `courses.code`와 교집합으로 매칭한다

- **결정**: 제목·설명·장소에서 숫자를 포함한 영숫자 토큰을 넉넉히 뽑고, 등록된 과목 코드와 일치하는 것만 채택한다.
- **이유**: 실물 MyWaseda ICS가 없어 코드 표기 형식을 확정할 수 없다. 매칭 판정을 DB의 실제 과목 코드가 하게 만들면, 형식이 `【…】`든 `(…)`든 맨 토큰이든 안 깨진다. 과다 추출은 등록된 코드와 안 맞으면 그냥 버려지므로 해가 없다.
- **버린 대안**: MyWaseda 형식을 추정한 좁은 정규식 — 기억으로 지어낸 형식이 틀리면 전부 미매칭이 된다.

## 2026-08-05 — sync-ics는 크론 스케줄에 넣지 않는다

- **결정**: `workflow_dispatch` 선택지에만 넣고 정기 스케줄은 비워뒀다. 정식 경로는 `/settings` 수동 업로드다.
- **이유**: MyWaseda가 구독 URL을 주는지 확정되지 않았다(SPEC 5.1b 미확정 항목). `WASEDA_ICS_URL` 없이 스케줄을 돌리면 매일 워크플로가 빨개진다.
- **버린 대안**: 스케줄에 넣고 URL이 없으면 200으로 조용히 넘기기 — "설정을 안 한 것"과 "동작한 것"이 로그에서 구분되지 않는다.

## 2026-08-03 — 퀴즈 보기는 저장 전에 서버에서 섞는다

- **결정**: `shuffleChoices()`로 보기 순서를 섞고 `answer_index`를 다시 계산한 뒤 저장한다.
- **이유**: 첫 생성에서 **5문제 전부 answer_index가 0**이었다. 모델이 정답을 첫 보기에 두는 경향이 강해서, 그대로 두면 항상 1번을 고르는 것만으로 100점이 나온다. 프롬프트로 부탁하는 것보다 서버에서 섞는 쪽이 확실하다.
- **버린 대안**: 프롬프트에 "정답 위치를 무작위로" 지시 — 통계적으로 치우침이 남는다.

## 2026-08-03 — 복습이 5문제를 채우면 AI를 부르지 않는다

- **결정**: `generate-quiz`는 복습 예정 문항 수를 먼저 세고 부족한 만큼만 생성한다. 0개면 AI 호출 없이 끝낸다.
- **이유**: 복습 문항이 이미 오늘 자리를 차지하는데 새 문항을 5개 더 만들면 예산만 쓰고 쌓인다.
- **버린 대안**: 매일 5문제 고정 생성 — SPEC 5.5의 월 예산 하드캡과 충돌한다.

## 2026-08-03 — 퀴즈 정답 인덱스를 DB 제약으로 강제

- **결정**: `quiz_questions`에 `check (answer_index >= 0 and answer_index < array_length(choices, 1))`를 걸었다. `difficulty`도 1..3으로 제한했다.
- **이유**: G2 조건이 "answer_index가 0~3 범위"를 요구한다. 생성 코드에서만 검사하면 AI가 범위 밖 값을 내놨을 때 조용히 저장된다. 선택지 개수와 연동해서 4지선다가 아닌 문항이 생겨도 자동으로 맞는다.
- **버린 대안**: `check (answer_index between 0 and 3)` — 선택지 개수가 바뀌면 같이 고쳐야 한다.

## 2026-08-03 — 브리핑 프롬프트에 URL 대신 기사 번호를 보낸다

프롬프트 구성을 실측했더니 **URL이 사용자 프롬프트의 79%** 였다. Google News 리다이렉트 URL이 평균 211자(최대 428자)로 제목(평균 46자)보다 5배 길다.

- **결정**: 프롬프트에는 `[3] 제목` 형태로 번호만 싣고, 모델은 `source_indices`로 답한다. `resolveSources()`가 번호를 실제 URL로 되돌린다.
- **이유**: 비용의 대부분이 정보가 아니라 URL 문자열이었다. 부수 효과로 **모델이 URL을 지어낼 수 없다** — 범위를 벗어난 번호는 서버가 버린다.
- **버린 대안**: 뉴스 건수 축소 — 브리핑 품질(섹터·언어 커버리지)이 직접 깎인다.

| URL 포함 | 18,764 | 4,354 | $0.1249 | $3.75 |
| 번호 방식 | 5,083 | 1,519 | **$0.0380** | **$1.14** |

출력도 65% 줄었다. 응답의 `source_urls`에 긴 URL을 되풀이하던 몫이 번호로 바뀌었기 때문이다.
$10 예산 대비 11%로 내려가 Phase 2의 퀴즈·자료요약 몫이 넉넉해졌다.

## 2026-08-03 — 부분 실패는 200, 전멸만 500

- **결정**: 소스 18개 중 일부가 실패하면 HTTP 200에 `failures`를 담아 돌려주고, 전부 실패했을 때만 500.
- **이유**: 소스 하나가 죽었다고 크론을 빨갛게 만들면 진짜 장애를 놓친다. 부분 실패는 `job_runs.meta`와 `sync_state`에 남아 배너로 드러난다.
- **버린 대안**: 실패가 하나라도 있으면 500 — 알림 피로가 쌓여 무시하게 된다.

## 2026-08-03 — 뉴스 중복은 url unique + ignoreDuplicates로 거른다

- **결정**: `news_items.url`의 unique 제약에 `ignoreDuplicates: true`로 upsert한다. 이미 있는 기사는 갱신하지 않는다.
- **이유**: 같은 기사가 여러 섹터·언어 피드에 동시에 나온다. 갱신하면 최초 수집 시점과 섹터가 덮여 브리핑 입력이 흔들린다.
- **버린 대안**: 제목 유사도 기반 중복 제거 — Phase 1에 필요 없는 복잡도다.

## 2026-08-03 — ctag는 이벤트를 실제로 가져온 뒤에만 전진시킨다

- **결정**: `upsertCalendars`는 ctag를 쓰지 않는다. 이벤트 upsert가 끝난 뒤 `markCalendarSynced`가 따로 기록한다.

- **버린 대안**: 한 번에 upsert — 코드는 짧지만 실패 시 복구가 안 된다.
