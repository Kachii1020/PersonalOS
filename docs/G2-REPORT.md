## 조건별 근거

### 1. 퀴즈 잡이 5문제를 생성하고 도메인이 2개 이상 섞인다 ✔

```
증거: 생성 2문제, 도메인 2종 ["accounting","system_design"]
```

복습 예정 3문제가 이미 있어 생성은 2문제였다. **복습 + 신규 = 5문제**가 오늘의 분량이고,
복습만으로 채워지면 AI를 부르지 않는다. 조건의 "5문제"는 오늘 푸는 문항 수로 판정했다.

### 2. 오답 처리 시 quiz_review_queue에 stage 1/2/3이 +1/+3/+7일로 생성된다 ✔ (수동)

**자동 테스트에 넣지 못했다.** 채점은 `/quiz`의 서버 액션이고 그 경로의 `recordAttempt`는
세션 쿠키(`cookies()`)를 쓴다. node 테스트에는 요청 스코프가 없어 직접 부를 수 없고,
서버 액션을 HTTP로 흉내내려면 빌드마다 바뀌는 action id에 기대야 한다.
리포지토리를 우회해 REST로 행을 만들면 검증 대상인 스케줄링 로직을 건너뛰게 된다.

브라우저에서 정답이 4번인 문항에 **1번(오답)**을 눌렀다.

```
--- 응시 기록 ---
 고른보기 | 정답여부
        0 | f

--- 복습 큐: JST 오늘로부터 며칠 뒤인가 ---
 stage |   due_on   | JST기준_일수
     1 | 2026-08-08 |            1
     2 | 2026-08-10 |            3
     3 | 2026-08-14 |            7
```

> 처음 `current_date`로 재봤을 때 +2/+4/+8로 나왔다. Postgres의 `current_date`가 UTC(8/6)이고
> 앱은 `lib/time.ts`대로 JST(8/7) 고정이라 생긴 차이였다. JST 기준으로는 정확히 +1/+3/+7이다.

```

```

(4×4.0 + 2×2.0 + 4×1.0) ÷ 10 = 2.40. 순수 함수(`tests/grades.test.ts` 5건)와
화면 표시를 둘 다 대조했다 — 함수만 맞고 화면이 틀리면 조건을 만족하지 못한다.

### 11. Notion 위키 항목이 앱에 표시되고, 앱에서 Notion을 수정하지 않는다 ✔

```
증거: Notion의 '(제목 없음)'이 /wiki에 표시됨, Notion 클라이언트에 PATCH/PUT/DELETE 0건
```

기대값은 앱을 거치지 않고 Notion API에서 직접 받아 대조했다. 앱 코드로 기대값을 만들면
앱이 틀려도 통과한다. "수정하지 않는다"는 실행으로 증명할 수 없어 소스 검사로 판정했다 —
`call()` 호출부가 전부 `/databases`·`/data_sources`·`/search`이고 쓰기 메서드가 0건이다.

## 게이트를 만들며 고친 것

- 자동 테스트 3건이 처음에 실패했는데 **전부 게이트 코드 문제였다.** `cookies()`와
  `unstable_cache`는 요청 스코프 밖에서 못 쓴다. 조건을 HTTP 검증으로 바꿨다.
- `assert(res.ok, await res.text())` 뒤에 `res.json()`을 부르면 "Body is unusable"이 난다.
  메시지 인자가 assert보다 먼저 평가되기 때문이다. G1에서 겪고도 또 했다 — `created()` 헬퍼로 묶었다.
- SSR은 JSX 보간을 텍스트 노드로 쪼갠다. `"복습 1문제"`를 통짜 문자열로 찾으면 안 잡힌다.
